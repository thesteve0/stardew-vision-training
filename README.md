# Stardew Vision Training Repository

**Model fine-tuning and dataset preparation for Stardew Vision accessibility project**

This repository contains all training, evaluation, and dataset preparation code for fine-tuning VLMs (Vision-Language Models) and OCR models for the [Stardew Vision](https://github.com/yourusername/stardew-vision) accessibility application.

---

## Purpose

1. **Fine-tune Qwen2.5-VL-7B** to recognize Stardew Valley UI screens and generate natural language narrations
2. **Prepare datasets** with real screenshots + synthetic augmentation
3. **Evaluate model performance** on tool calling accuracy and narration quality
4. **Support conference talks/workshops** on VLM fine-tuning for accessibility

## Quick Start

### 1. Clone and Setup

```bash
# Clone this repo
git clone https://github.com/yourusername/stardew-vision-training.git
cd stardew-vision-training

# Open in devcontainer (VS Code)
# Or manually install dependencies:
uv sync
source .venv/bin/activate
```

### 2. Collect Screenshots

See [`docs/phase2-collection-plan.md`](docs/phase2-collection-plan.md) for collection guidelines.

```bash
# Organize a screenshot
python scripts/annotation/organize_screenshot.py \
  /path/to/screenshot.jpg \
  --screen-type tv_dialog \
  --name tv_weather_01
```

### 3. Fine-Tune Qwen

```bash
# Prepare training data (real + synthetic)
python synthetic_data/generate_variations.py \
  --screen-type tv_dialog \
  --num-variations 100

# Train with LoRA
python fine_tuning/qwen/train.py \
  --config fine_tuning/qwen/lora_config_local.yaml \
  --output-dir experiments/qwen-tv-fish-v1
```

### 4. Build and Deploy to OpenShift AI

Training can run distributed on OpenShift AI via KubeRay. The container image is built locally and pushed to the cluster's internal registry.

**Prerequisites**: `podman` (or `docker`), `oc` CLI logged into the cluster.

```bash
# One-time: authenticate with the Red Hat container registry
podman login registry.redhat.io
# Use your Red Hat account credentials (e.g., steve.pousty@gmail.com)

# Build the training image (deps cached, only code layer rebuilds on changes)
podman build -f deploy/Dockerfile -t localhost:5000/stardew-vision-training/stardew-training:latest .

# Port-forward to the OpenShift internal registry
oc port-forward svc/image-registry -n openshift-image-registry 5000:5000 &

# Authenticate with the internal registry using your OpenShift token
podman login --tls-verify=false localhost:5000 -u $(oc whoami) -p $(oc whoami -t)

# Push the image
podman push --tls-verify=false localhost:5000/stardew-vision-training/stardew-training:latest

# Verify the image landed
oc get istag stardew-training:latest -n stardew-vision-training

# Submit a training job
oc apply -f deploy/rayjob.yaml

# Or run evaluation on the cluster
oc apply -f deploy/eval-job.yaml
```

The training data and checkpoints are mounted via PVCs (`training-data` at `/data`, `training-checkpoints` at `/checkpoints`), not baked into the image.

### 5. Evaluate

```bash
# Evaluate tool calling accuracy
python evaluation/eval_tool_calling.py \
  --model experiments/qwen-tv-fish-v1 \
  --test-set datasets/splits/test.jsonl

# Evaluate narration quality
python evaluation/eval_narration.py \
  --model experiments/qwen-tv-fish-v1 \
  --test-set datasets/splits/test.jsonl
```

### 6. Push to HuggingFace Hub

```bash
python scripts/upload_to_hub.py \
  --model-path experiments/qwen-tv-fish-v1 \
  --repo-id yourusername/stardew-vision-vlm \
  --version v1
```

## Dataset Design

### Synthetic data

The three tool-calling classes (caught_fish, pierre_shop, tv_dialog) have synthetic training data generated by compositing varied text onto clean background screenshots. This works because those screens have predictable layouts with variable text content.

### no_tools (negative/rejection class)

The `no_tools` class has **no synthetic data** — only real game screenshots. The "no tool needed" class covers every screen that *isn't* one of the three tool-specific patterns — overworld exploration, menus, cutscenes, combat, farming, etc. The visual variation is too broad to synthesize meaningfully.

**Split strategy**: `data_prep.py` handles no_tools differently from the tool-calling classes:

1. Tool-calling classes are split at the standard 85/15 train/val ratio
2. no_tools training is **capped at 2:1** relative to the average tool-class training count (~310 no_tools vs ~155 per tool class)
3. Remaining no_tools examples **overflow into validation** (~63 vs ~28 for other classes), giving stronger val loss signal on the hardest class

**Why 2:1**: The universe of "no tool needed" screens is orders of magnitude larger than any specific tool screen. Research on out-of-scope detection (Larson et al. 2019, EMNLP) and function-calling models (Patil et al. 2023, Gorilla) converge on ~2:1 negative-to-each-positive as the sweet spot. Beyond 3:1 the model starts over-rejecting valid tool calls. Validated empirically: a tiny run with balanced 1:1 data collapsed no_tools accuracy to 0%.

Hard negatives — screens visually similar to tool screens but not matching them (e.g., NPC dialogs that aren't TV, other shop menus, inventory screens) — are particularly valuable.

### Evaluation set

125 images held out in `datasets/eval_set.json` — **never** used for training or validation:
- 25 each for caught_fish, pierre_shop, tv_dialog
- 50 for no_tools (larger because it's the hardest class with widest visual variation)

## Training Data Format

### ChatML Conversation Example

```json
{
  "messages": [
    {
      "role": "user",
      "content": [
        {"type": "image", "image": "data:image/png;base64,..."},
        {"type": "text", "text": "What's on this screen?"}
      ]
    },
    {
      "role": "assistant",
      "tool_calls": [
        {
          "function": {
            "name": "crop_tv_dialog",
            "arguments": "{\"image_b64\": \"...\"}"
          }
        }
      ]
    },
    {
      "role": "tool",
      "name": "crop_tv_dialog",
      "content": "{\"dialog_text\": \"...\"}"
    },
    {
      "role": "assistant",
      "tool_calls": [
        {
          "function": {
            "name": "text_to_speech",
            "arguments": "{\"text\": \"TV weather forecast: ...\"}"
          }
        }
      ]
    }
  ]
}
```

This trains Qwen to:
1. Classify screen type → call correct extraction tool
2. Parse OCR results → generate natural narration

## Key Technologies

- **VLM**: Qwen2.5-VL-7B-Instruct (7B parameters, FP16 only on ROCm)
- **Fine-tuning**: LoRA via PEFT + TRL SFTTrainer
- **OCR**: PaddleOCR (PP-OCRv5, CPU-only)
- **Distributed Training**: Ray Train on OpenShift AI
- **Experiment Tracking**: MLFlow
- **Synthetic Data**: LLM-based (Claude/GPT-4) variation generation

## ROCm Constraints

**CRITICAL**: This project runs on AMD ROCm 7.2 (Strix Halo gfx1151).

- **FP16 only** — No BF16, no INT4, no INT8
- **PaddlePaddle 3.2.0** — Version 3.3.0 has OneDNN PIR bug
- **Never `pip install torch`** — Use ROCm-provided build
- **Use `uv` for package management** — Protects ROCm packages

See `template_docs/notesOnRocm72.md` for details.
